## Step Granularity — One Step Per Concern

Each workflow step (a catalog tool) handles **one concern**:

- **Data processing** (matching, filtering, calculations, tagging) → use the catalog's data/aggregation/judge tools (`aggregate_data`, `get_data`, `judge_data`, `save_data`).
- **Each report or output format** → a separate step. A `chat_download` node delivers the HTML artifact.
- **Don't split data processing into unnecessary sub-steps.** Group, sum, and count in one `aggregate_data` step where possible.
- **Don't combine data processing with presentation.** Keep the computation step and the `chat_download` delivery step separate.

### Why

- Intermediate results are persisted under concrete `staging_*` names so they are auditable and can be read by later steps.
- Delivery steps (`chat_download`) are swappable — replace an exception report with an aging report without touching the data processing.

### HTML and reports

Reports are delivered with a `chat_download` node, not generated by a workflow step. A workflow step must never call a free-form LLM to generate HTML.

For a **drill-down** table report (summary rows that expand to their detail rows), build it deterministically with the `report_table` tool, then deliver with `chat_download`:

```json
{ "label": "Build Report", "tool_id": "report_table",
  "tool_parameters": { "summary": "staging_ic_gl_summary", "details": "interco_audit_demo_ic_transactions", "group_by": ["GL Account"], "detail_columns": ["Txn ID", "Date", "Memo", "Amount (USD)"], "title": "Amount by GL Account" } },
{ "label": "Download Report", "tool_id": "chat_download",
  "tool_parameters": { "data": "{{result}}", "filename": "report.html" } }
```

`report_table` reads the summary (`staging_*`) and detail data files, joins on `group_by`, and returns a styled, self-contained HTML document (brand tokens + provenance band + expandable rows). Persist the summary to a `staging_*` table first (`save_data(name="staging_…", value="{{result}}", type="json_array")` after `aggregate_data`).

For a **flat** table with no drill-down, `chat_download` with `widget="data-table"` + JSON `data` is acceptable. Never pass a bare JSON array as `data` without either `report_table` or a `widget`.
